## Priority observations

### FIN-01 — Label-cost reversal retry changes its request payload

Source-confirmed; high financial correctness priority. Initial request in
`src/app/api/orders/[id]/label/route.ts:351-379` uses metadata reason
`label_cost_deduction`; `src/lib/labelClawbackRetry.ts:44-61` retries with
`label_cost_deduction_retry` under the same deterministic key from
`src/lib/labelClawbackState.ts:70-77`. Initial catch covers provider success
followed by failed local finalization. This is not an exact request replay.

Conditional consequence, not demonstrated duplicate debit: ambiguous provider
success, absent durable acknowledgement, eventual provider key pruning and
sufficient unreversed balance could allow another deduction. Provider behavior
has not been exercised. SQL retry backoffs total over 31 hours before attempt
five (`20260901140000_prepare_order_label_authority/migration.sql:861-877`).
Normal durable success is excluded, and generation fencing/row locks remain.

Required follow-up: one immutable request builder; provider identity recovery
before ambiguous replay; bounded idempotency age. Tests must cover exact payload
equality, response loss, failed local finalization and late retry.

### MSG-01 — Fallback polling exhausts its own allowance

Independently source-confirmed by parent and scalability worker.
`src/components/ThreadMessages.tsx:262-291` polls every three seconds after SSE
failure. `/api/messages/[id]/list` uses the shared user limit of 240/hour
(`src/lib/ratelimit.ts:90-94`). `src/lib/messageStreamState.ts:1-8` treats 429 as
terminal; the component clears the timer without timed recovery. With unused
quota, continuous successful fallback consumes 240 reads in about 12 minutes.
Other tabs/history requests shorten that window. Normal uninterrupted SSE does
not use this limiter. This is a runtime defect, not a cross-user disclosure.

Required follow-up: align polling and quota, respect Retry-After, bounded SSE
reconnection, hidden-tab backoff; hour-long and multi-tab regression tests.

### JOB-01 — Clawback provider deadline exceeds the worker budget

Worker source finding; parent validation pending. Handler has 60-second maximum
and claims ten rows before serial provider calls (`src/app/api/cron/label-clawback-retry/route.ts:9-28`,
`src/lib/labelClawbackRetry.ts:27-95`). Installed Stripe SDK defaults to an
80-second request timeout, with network retries; `src/lib/stripe.ts:7-9` does not
override it. SQL increments counts at claim, then stale claims recover after
30 minutes. A stalled first call can strand the rest of the already-claimed
batch and consume claim counts without corresponding provider attempts.

Half-hour schedule allows at most 20 attempts/hour (480/day), not that many
successful recoveries. SQL has SKIP LOCKED, generations and stable ordering;
this is not an unfenced loop. Measure backlog age, align request/deadline budgets,
claim near execution, and separate claimed from actually attempted counts.

### JOB-02 — Monthly guild processing has no durable continuation

Worker source finding; parent validation pending. `src/app/api/cron/guild-metrics/route.ts:35-111`
allows 300 seconds, pages 50 sellers and processes three concurrently.
`src/lib/cronBatchState.ts:6-38` begins at a null cursor and continues to exhaustion;
there is no saved cursor or total deadline. Cleanup follows the entire seller
pass. `CronRun` records status, not continuation, and only FAILED—not stranded
RUNNING—runs are reclaimable. Pagination bounds memory, not total work.

At sufficient workload, the same tail can remain stale after repeated restarts.
No measured safe seller count. Persist cursor/generation, stop before the hard
deadline, reclaim stale leases with fencing, and schedule retention separately.
